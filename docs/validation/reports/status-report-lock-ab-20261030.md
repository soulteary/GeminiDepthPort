# 状态报告锁占用优化 — 2026-10-30

基线 `4c225850a3abec2d8abf4c24555074bad68213c0`。前后生产代码只改变报告的锁边界；没有混入时间戳或 SDK 策略修正。[原始结果及可执行文件 SHA256](status-report-lock-ab-20261030.json)。

## 修改

- RawRecorder 状态锁内只复制有界标量、快照 ID 和 diagnostics Arc；释放后再调用队列/磁盘报告并构造 JSON，避免嵌套报告锁。
- 录制队列复制计数、最老入队年龄和固定 513 桶等待直方图，释放队列锁后计算分位数与 JSON；没有复制帧、像素或 IMU 队列。
- 磁盘统计复制六组固定直方图及有界失败计数，释放锁后计算分位数、构造 JSON。检查点观测本身原已在锁外构造，继续保持。
- 状态落盘统计只复制 wall 直方图、序号、错误布尔值和 pending 数量；释放锁后格式化。pending Batch 的 JSON 和错误字符串不被复制。

每次报告重新取快照，不缓存旧报告，不改变字段、报告触发、心跳频率、pending 容量、关键状态等待和 fsync/rename 顺序。各锁内字段是一致快照；队列、采集状态、IO 统计仍是不同时间点的诊断视图，不能当作全局事务快照。关键 Complete 状态的推进条件未改变。

最终 JSON 字节编码与原子落盘原已在后台线程、锁外执行；这次移出锁的是报告值构造与直方图计算，没有改动落盘协议。两轮实际读回、逐帧/索引哈希、提交守卫和崩溃恢复路径均未修改。V3 保留前缀验证及最终全量验证；V2 保持原有最终验证。

## 服务级性能

Linux ARM64 Docker，Rust 1.90 release/thin LTO，同一公共测试驱动分别调用原始/优化服务。每种观测开关、每个版本 5 轮，逐轮反转前后顺序，共 20 次。每次 240 对 640×400 图像，合成 SDK wait=33 ms、两路 IMU 各请求 200 Hz，chunked-v3 流水线，写入队列容量 4。两版显式使用相同 50 ms 心跳与 500 ms 心跳超时；大图像夹具默认 100 ms，因此驱动在计时前显式覆盖，未改变产品配置。

CPU 是 ready 到录制 complete 的 worker+supervisor user/system ticks 增量除以墙钟，统计粒度为系统时钟 ticks。RSS 是 worker 从进程开始到该测点的 VmHWM，不是匿名内存或整个容器工作集；supervisor 峰值另列原始数据。追加 P99 是全录制 240 次 append 的直方图区间边界中位数，含就绪前少量记录，不能视为精确分位数。心跳间隔是父测试轮询观察到的新序号时间差，包含轮询/调度/原子落盘影响，不是精确写入周期。

本实验没有真实 USB、DDS、外部录制器或实际磁盘延迟负载。计时期间没有并行编译或程序测试；模拟库在每次启动前构建。所有数值为五轮中位数，另明确列出心跳全轮最大值。

- 检查点观测关闭：CPU 0.2311 → 0.2339 核（+1.2%）；追加 P99 [2.884, 3.146] → [3.146, 3.408] ms；worker 峰值 RSS 9104 → 9056 KiB。
  每轮最大观察心跳间隔的中位数 87.23 → 87.35 ms；所有轮最大值 89.19 → 165.21 ms；IMU 提交样本范围 before 3202–3226，after 3207–3220。
- 检查点观测开启：CPU 0.2500 → 0.2476 核（-1.0%）；追加 P99 [1.704, 1.835] → [2.359, 2.513] ms；worker 峰值 RSS 9616 → 9544 KiB。
  每轮最大观察心跳间隔的中位数 84.64 → 82.96 ms；所有轮最大值 94.80 → 204.85 ms；IMU 提交样本范围 before 3121–3146，after 3110–3142。

CPU 基本持平，不能宣称整体 CPU 降低；追加 P99 没有改善，观测开启组区间上界反而由 1.835 增至 2.513 ms。RSS 略低，但这不是匿名内存降低或稳定内存节省的证据。观测心跳最坏间隔增大，最大约 205 ms，仍低于相同 500 ms 超时；全部运行无心跳过期重启，不能宣称心跳最坏延迟改善。移锁并未减少总直方图/JSON 工作量，还增加了有界复制，因此不承诺所有负载均加速。

## 独立锁竞争实验

同一 release 单元测试驱动在原基线/优化库中运行，六组直方图使用相同固定样本；一线程连续构造 2000 个报告，另一线程不断获取 IO stats 锁并更新一个标量。各 5 轮交替顺序。它刻意制造竞争，不写图像、不运行 SDK、不代表 append 或磁盘吞吐；不与上述 CPU/内存结果混用。

- before：统计更新锁等待均值中位数 3.491 μs；等待 P99 区间上界中位数 81.919 μs；更新次数中位数 7476；2000 次报告墙钟 26.16 ms。
- after：统计更新锁等待均值中位数 0.138 μs；等待 P99 区间上界中位数 0.087 μs；更新次数中位数 212476；2000 次报告墙钟 33.72 ms。

锁等待明显缩短，但报告线程墙钟上升，而且更新线程完成的工作量不同，不能把更新次数直接折算为生产加速率。这项实验支持“昂贵格式化不再占用统计更新锁”的结论，不支持服务 CPU/P99 普遍改善。

## 验证与保障

完整 Rust 工作区、63 项外部集成检查、全部目标 Clippy 和格式检查通过；生产 Rust 行覆盖率 18919/19102 = 99.0420%，原过滤规则与 99% 门禁不变。新增确定性并发测试在格式化阶段暂停报告，确认录制状态/IO 更新可继续、旧快照保持一致、新报告反映新值；关键持久化提交在报告暂停时仍可完成，并继续等待原写入回调完成。队列快照在持有原队列锁时可独立格式化，且不复制载荷。

既有慢状态 fsync 时持续发布、关键状态提交等待、失败持久化、最终 stopped 状态、队列溢出、IMU、哈希篡改拒绝、两轮读回计数与 SIGKILL/恢复测试继续通过。20 次性能运行均核对原生 240 对完成、图像/IMU 实际读回数恰为提交量两倍、零写入队列溢出、无拒绝/缺失对；停止后再确认 stopped 和原生 complete 状态。
