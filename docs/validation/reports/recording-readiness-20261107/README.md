**没有解决全部部署阻断。** 持续录制 `RAW_QUEUE_OVERFLOW`、SDK 深度源序号缺口和正式六组／独立相机恢复验收仍未关闭。本轮没有把 CI、短合成测试或恢复合同回归当作生产可用证明。运行条件及新目录命令见[验收说明](../../recording-readiness.md)。

本轮修正正式源缺口门禁、启动容量估计、运行中/backing 可用空间保护，以及 trace 错误期间丢失计数器被跳过但仍显示 0 的问题。trace v2 将不可确认的丢失数写为 null，保留原始错误；256 KiB 输出缓冲保持字节上限及两秒排空期限。合成适配器新增有界、连续 checkpoint 事件文件，缺失历史不再静默当作完整诊断。

完整额度批次保留为显式候选，生产默认仍为半额度。候选与原策略的未确认总额度、队列、五道同步、读回、哈希和恢复要求相同；减少同步次数不足以证明持续可靠性，不默认启用。旧 checkpoint-worker 候选补丁未应用或修改。

本地软件验证通过：Python 544 项、0 失败、8 项按环境跳过；Rust workspace 和外部录制／恢复回归通过；生产 Rust 行覆盖率 19,623 / 19,814（99.036%）；Rust 1.85.0 全数据平面目标 clippy 警告为零。真实内核合同样本取得 988 事件、60 次真实 fsync 全部配对，计数器完整、零丢失、尾部无未配对，清理成功；该样本每 CPU ring 为 1 MiB、输出缓冲 256 KiB，不是录制或相机验收。

三 writer 对照每组请求 **20 秒／每 writer 600 对**，不是 600 秒。三轮交替结果：正常延迟下两种策略各仅 1/3 组全部完成；额外 payload fsync 300 ms 时半额度 0/3、完整额度 1/3；900 ms 时均 0/3。其他组明确失败。不能把截短失败组的低 CPU 或 RSS 用作性能收益；`validation.json` 仅保留第一轮双方都完成时的描述性数据，整体结论为未获得稳定收益。

额外 600 秒宿主绑定目录计划约 1.04–1.09 秒就溢出，on／正式恢复未运行，trace 也不完整。较早 loopback 计划遭遇 backing 空间不足，属于环境失败，不计性能结果；镜像保留，之后只对已读确认为全零的区间回收物理分配，完整镜像 SHA256 前后一致。大部分异常空间占用在卸载结束后已释放，不能把恢复的全部空间归因于零区间回收。该新镜像的一部分 ext4 目录只读导出时返回 Bad message，未修复、未删除或宣称可恢复。所有这些失败日志保留。
