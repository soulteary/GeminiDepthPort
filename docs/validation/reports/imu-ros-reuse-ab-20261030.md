# IMU ROS 消息复用与共享 context 验证（2026-10-30）

基线：`1b4ef7e2a4427d2bd4e58ae80a5f19e666d7039f`。优化实现与本报告一起提交。

## 改动与采用结论

IMU 两类消息各预建一个模板，初始化时复制 frame ID 并设置未知姿态/未测量分量协方差。每次先执行原有数值、时间戳与单调性检查，再完整更新 header 时间戳和对应三轴值，通过同步 publish(const&) 发布。没有共享两类传感器的消息对象，不保留调用方 frame 指针。显式关闭 intra-process 通信；不承诺 rclcpp/RMW 零分配、DDS 零复制或已经送达。

新增可选 context v1 C ABI 和线程内 Rust 租约。共享在调用方显式创建的租约内进行，不按命名空间或全局缓存自动合并。图像与 IMU 发布器持有自己的共享所有权；先销毁调用方租约、图像或 IMU 都不会关闭其他发布器，最后一个持有者才 shutdown。同一动态库引用随租约保留，不能跨库混用句柄；Rust Rc 保证不可跨线程。旧的独立创建 API 和 image ABI v1 不变。

启用 IMU/ROS 且库完整支持扩展时，采集路径为彩色、深度与 IMU 的三个独立节点共用一个 context。完全没有扩展的旧桥保持独立模式；扩展不完整、版本不符或创建失败则报错，避免混用不同生命周期。图像 QoS 仍为 reliable/volatile/KEEP_LAST(10)，IMU 为 reliable/volatile/KEEP_LAST(100)，并继续检查本地实际 QoS。TF/诊断辅助发布器本轮保持独立，因此整个 Rust 采集服务并非只有一个 ROS context。

评估结果支持采用共享路径：会话内参与者身份和销毁隔离已通过真实中间件验证，资源占用明显减少。没有测得稳定的整体 CPU 或 IMU 发布 P99 提升。仅复用消息时也没有足够证据宣称整体 CPU 显著下降。

## 功能与数据保障

Linux 全 Rust 工作区、外部集成测试、全部目标 Clippy、格式检查通过。联合生产行覆盖率 18494/18670 = 99.06%，原统计口径和 99% 门禁不变。该覆盖率只针对生产 Rust，不代表 C++ 行覆盖率。

Rust 动态 ABI 测试验证共享库租约、发布器持有 context、旧桥完整回退、部分符号拒绝、版本错误、创建失败、错误但返回非空句柄、成功但返回空句柄的清理；采集服务测试确认实际选择共享路径和旧桥仍能达到 readiness。

真实 Humble/Fast DDS 的全部既有 smoke 通过：图像字节、CameraInfo、metadata、系统/global 映射、QoS、TF、诊断及多相机静态变换。新增 smoke 通过 endpoint GID 前缀验证同一会话的 Image/CameraInfo/metadata/accel/gyro 使用同一 DDS 参与者，两个显式会话保持不同参与者。测试先释放租约再释放图像并继续发布 IMU，再以相反顺序销毁另一会话，确认互不关闭。失败创建不影响其他发布器。

新测试每条消息变更三轴值并交替使用 system/global 映射，验证无跨传感器残留和旧值污染；NaN 或缺失 global 被拒绝后，同序号合法消息仍可发布，避免错误调用推进状态。协方差和未知姿态标记保留。既有 ROSbag2 SQLite3 逐条 CDR SHA-256 读回与有效数值篡改拒绝继续通过。

未修改 SDK 时间戳规则，也未实现物理设备的时间戳兼容修正；本轮合成验证不能代替真实设备验收。没有改动内置录制格式、队列、哈希、fsync、提交守卫或恢复规则：chunked-v3 检查点累计读回加最终全量读回仍保留，旧 files-v2 保持原有提交前全量验证。完整 Rust 测试继续核对双轮计数、哈希损坏拒绝和崩溃恢复。

## 性能方法

三组各 5 轮，共 15 个独立容器进程，交替并反转顺序。before 使用冻结基线桥；reuse 使用新桥但独立创建三个 context；shared 使用新桥共享一个 context。两版动态库 SHA-256 与每次原始数据见同名 JSON。性能期间没有并行编译或其他测试。

测试为 ARM64 主机上仿真执行的 AMD64 ROS Humble/Fast DDS；实际 C++ 桥与中间件，Python ctypes 驱动。两个图像发布器使用合成 640×400 YUYV 与毫米深度，目标 30 FPS；两路原始 IMU 目标各 200 Hz，frame ID 长于常见 SSO 长度。无图像/IMU 下游订阅者，不运行 SDK、USB、Rust 采集服务、原生录制或 ROSbag2 录制。ROS_DOMAIN_ID=91。不能将本表 CPU 当作整个采集进程或三机容器 CPU，也不能与匿名内存/容器工作集直接比较。

创建后预热 1 秒，再测 8 秒。CPU 为进程所有线程 user+system 增量除以墙钟时间；RSS/VmHWM 来自 /proc/self/status，线程数是该进程线程总数，不是单独统计 DDS 线程。发布延迟包含 Python ctypes 调用与 C++ 同步 publish，不是下游送达延迟；P99 为该轮样本排序后的 nearest-rank。

调度器不追赶错过的 IMU 周期，实际总发布率约 377–384 次/秒，即每路约 189–192 Hz，未达到目标每路 200 Hz；图像约 30 对/秒。此驱动用于同负载相对对照，不能据此证明 200 Hz 实机连续性、零丢样或最大吞吐。

## 五轮中位数

- before：CPU 0.3271 核；RSS 145808 KiB；线程 24；IMU 发布平均 27.338 μs / P99 100.415 μs；创建 164.760 ms / 销毁 35.001 ms。
- reuse：CPU 0.3243 核；RSS 145832 KiB；线程 24；IMU 发布平均 24.905 μs / P99 96.832 μs；创建 170.594 ms / 销毁 34.993 ms。
- shared：CPU 0.3232 核；RSS 139864 KiB；线程 10；IMU 发布平均 25.180 μs / P99 106.165 μs；创建 140.657 ms / 销毁 26.641 ms。

共享模式相对基线：context 3→1，进程线程 24→10，RSS 145808→139864 KiB，减少 5944 KiB（约 5.80 MiB）；创建耗时 164.760→140.657 ms，销毁 35.001→26.641 ms。共享模式只计这三个节点，Rust 辅助发布器不在该进程基准中。

CPU 范围：before 0.3204–0.3392、reuse 0.3217–0.3253、shared 0.3166–0.3333 核。IMU 发布 P99 范围分别为 67.749–227.704、80.166–165.164、86.499–204.413 μs。区间重叠明显；共享模式 P99 中位数略高于基线，不能称为延迟全面改善。实际 IMU 调用率中位数为 381.98 / 382.52 / 382.07 次/秒，图像为 30.084 / 30.087 / 30.091 对/秒，未观察到有意义的吞吐变化。

没有重跑整个 Rust+SDK+原生录制的吞吐或追加 P99；本轮没有改动录制写入路径，采用发布桥阶段对照与完整录制功能回归。物理相机及实际订阅/录制负载下仍需对照验收。

## 复现

先将旧/新桥分别构建到可运行 Humble 的镜像。脚本在源码 ros/tests 下执行，通过 --mode before/reuse/shared 选择旧独立、新独立、新共享三个场景，轮换顺序，各 5 次。

```sh
ROS_DOMAIN_ID=91 python3 ros/tests/benchmark_imu_ros.py \
  --library /absolute/libgeminidepthport_ros_bridge.so \
  --mode shared --seconds 8 --repeat 0 --output /absolute/shared-0.json
```

真实功能测试：`bash ros/tests/run_smokes.sh`。无需物理相机。性能脚本为手动执行，不添加嘈杂的 CI 性能门禁；CI 继续执行功能、生命周期、QoS、哈希与覆盖率门禁。
