# IMU 配置缓存与计时拆分验证（2026-10-30）

优化前提交：`b17f87377b78c58ff9b6aee9fb8d413b83ec3214`。本报告与优化实现一起提交。新增不可变 `ValidatedImuConfig`，SDK 回调、ROS 发布器各自建立绑定；原生录制写入器和每次读回器从各自验证过的快照重新建立配置/消息时钟绑定。逐样本不再校验固定采样率、量程和配置字符串，也不再逐批反序列化快照 IMU/acquisition。

每条样本的有限数值、frame ID、时钟范围、序号和时间戳严格递增检查保留；global 必需性保留。未改变录制格式、两轮实际读回、逐帧/索引哈希、检查点、fsync、恢复或队列上限。未实施缓冲区复用、ROS context 共用和异步发布。

Linux 全工作区 Rust 测试、追加边界测试、全部目标 Clippy 和格式检查通过。覆盖率保持原口径：18225/18397 = 99.07%，高于 99% 门禁。

新增测试覆盖配置不可变、非法配置不能构造缓存、缓存与旧校验路径均拒绝异常数值/来源/时钟回退、禁用与 global 策略，以及写入器和独立读回器在打开时拒绝语义非法但内容哈希有效的快照。原有 files-v2、chunked-v3 双读回、两种检查点模式、哈希损坏和崩溃恢复测试继续通过。新计时测试注入首条 ROS 发布 150 ms 延迟，核对独立排空/发布统计、pump 总时长及无 ROS 时发布计数为零。

首次主机全工作区测试受沙箱限制无法监听本地 HTTP 端口；完整测试改在 Linux 容器运行。首次未带 init 的容器不能回收被 SIGKILL 监督器留下的僵尸进程，既有孤儿进程测试失败；带 `--init` 的完整复核通过，未更改生产逻辑或该测试断言。

远程覆盖率测试还暴露了“缺色时独立发布 IMU”功能测试的夹具问题：模拟 SDK 忽略配置采样率，始终以 200 Hz 双流产样；共享 runner 启动阶段约 650 ms 的文件同步阻塞触发了正确的 128 条队列溢出保护。修正夹具使采样周期及时间戳按 SDK profile 产生，并为该独立性测试显式选用 25 Hz；新增 SDK 子进程用例核对 25 Hz 的 40000 μs 序号/时间戳步长。生产队列、超时、溢出规则均未改变，200 Hz 测试、性能负载和独立溢出测试继续保留。修正后 SDK/采集包完整 Linux 测试及全部目标 Clippy 通过。性能观测采集于此测试夹具修正前，所用生产二进制与本次修正无关，200 Hz 采样周期仍为 5000 μs。

## 计时口径

- `pipeline_timing.sdk_wait_call`：仅 `pipeline.wait`，含超时/错误；前后 IMU pump 与录制缓冲均排除。SDK 返回 Unix/单调时间在 IMU 发布前获取。
- `imu.drain_wall`：每次 pump 的计数读取、SDK 队列排空与锁等待，包含失败。
- `imu.ros_publish_wall`：每个非空发布批次内所有同步 ROS 调用，包含失败；没有 ROS、预热排除和空批次不计入。
- `imu.pump_wall`：整个 IMU pump，包括统计开销，不含录制缓冲。

发布统计的分位数单位是批次，不是单条样本，也不是 DDS 送达时间。不同统计的样本集合不同，P99 不能相加；测试比较的是累计耗时。旧版 SDK 等待含 IMU pump，不能拿拆分后的下降作为 SDK 加速证据。

## 性能方法

ARM64 主机上原生运行 aarch64 Linux Docker，Rust 1.90 release，模拟 SDK 和模拟 ROS C ABI 发布桥，无实际相机/USB/DDS。图像为 640×400 YUYV/Y16，名义 30 FPS；IMU 加速度计与陀螺仪各 200 Hz。

先冻结旧版本并分别执行旧/新各 20 次探索性测试：仅发布/同步 chunked-v3 录制、IMU 开关、各 5 次；发布窗口 2 秒，录制目标 60 对。短窗口 CPU 存在明显波动，因此追加主要对照：同一驱动、同一容器交替运行旧/新服务，两个场景各 5 次，两版均开启 IMU；仅发布就绪后测 10 秒，录制就绪后测到 300 对完成。反转每轮版本顺序，运行期间没有并行编译或其他测试。原生录制上限 1 GiB，目标图像约 292.97 MiB。

CPU 为 worker 与 supervisor 的进程时间增量之和除以墙钟窗口，排除测试驱动和 fixture 编译；RSS 为两个进程各自 VmHWM 之和，不是同时刻峰值或匿名内存。录制追加/验证统计覆盖整次录制，包含就绪前已写入部分。P99 使用既有固定直方图分位上界。每次录制都要求目标完成、无图像拒绝/缺对，IMU 验证样本数等于提交数两倍。

## 主要结果：交替长窗口，5 次中位数

- 仅发布，before：吞吐 27.6985 对/秒；CPU 0.1010 核；峰值 RSS 合计 8872 KiB。
- 仅发布，after：吞吐 27.8976 对/秒；CPU 0.1030 核；峰值 RSS 合计 8896 KiB。
- 原生录制，before：吞吐 27.3333 对/秒；CPU 0.2126 核；峰值 RSS 合计 11328 KiB。
- 原生录制，after：吞吐 27.4984 对/秒；CPU 0.2016 核；峰值 RSS 合计 11176 KiB。

原生录制的追加 P99 上界为 18.874 → 17.622 ms，累计验证耗时为 410.335 → 389.828 ms。验证累计耗时范围分别为 381.712–442.060 / 360.197–407.892 ms。验证单次调用 P99 为 150.199 → 156.463 ms，说明不能把累计耗时下降理解为所有尾延迟都改善。

录制 CPU 范围为 0.1905–0.2356 / 0.1917–0.2170 核；仅发布 CPU 范围为 0.0910–0.1030 / 0.1000–0.1100 核。两版队列峰值均为 14/128。仅发布吞吐范围为 27.598–27.898 / 27.398–27.899 对/秒；录制吞吐范围为 26.821–27.615 / 27.402–27.799 对/秒。区间有重叠，不宣称稳定的整体吞吐或内存收益。

短窗口探索性结果同样保留：仅发布开启 IMU 时 CPU 0.0850 → 0.0950 核，原生录制 0.1719 → 0.2070 核；对应吞吐 26.9932 → 26.9934、27.8721 → 27.5940 对/秒；原生追加 P99 16.528 → 16.817 ms、验证累计 84.456 → 79.865 ms。没有丢弃这组较差结果；它说明低负载短窗口和磁盘/调度波动会掩盖微小固定开销变化。

## 逐样本微基准

同一优化后二进制分别执行仍保留的旧 `accept` 与新 `accept_validated` 路径；两者共用同一逐样本数据检查函数，差异是是否重复校验固定配置。使用 black_box 防止编译器将配置检查外提，每条样本推进序号和时钟。每种 frame ID 长度，交替运行两路径各 7 轮、每轮 500000 条；绑定创建成本在循环外。

- 20 字符 frame ID：20.303 → 3.405 ns/条，中位耗时下降 83.23%。
- 240 字符 frame ID：203.916 → 5.885 ns/条，中位耗时下降 97.11%。该长度用于展示字符串检查成本，不代表日常配置。

这证明固定配置校验已移出热路径，不代表整条采集 CPU 同比例下降。长窗口原生录制的 CPU、追加 P99 和累计验证中位数有所下降，仅发布 CPU 基本持平；实机收益仍需目标相机、原生 ROS 与实际录制负载验证。

## 复现

先冻结并构建旧提交的 release capture-service，保留其绝对路径；在新版本下执行：

```sh
GDP_IMU_BENCH_BASELINE_SERVICE=/absolute/before/capture-service \
GDP_IMU_BENCH_OUTPUT=/absolute/paired.json \
cargo +1.90.0 test --release --locked -p capture-probe --test service_supervision -- --exact imu_capture_ab_benchmark --ignored --nocapture

GDP_IMU_CACHE_MICRO_OUTPUT=/absolute/micro.json \
cargo +1.90.0 test --release --locked -p capture-contract --test imu -- --exact imu_validation_cache_benchmark --ignored --nocapture
```

不设置基线服务路径时，采集 benchmark 保留原有 IMU 开关短窗口模式。Linux 容器运行测试时使用 `--init`。同名 JSON 保存 60 次采集运行、28 轮微基准、二进制 SHA-256 和覆盖率摘要；均未将模拟数据描述为实机验收。
