# IMU 有界缓冲区复用验证（2026-10-30）

基线提交：`ecf615c3a1923d33fb6d8e3601b6e4ac5be1e803`。本报告与优化实现一同提交。

## 实现与边界

- 原有 `ImuSample` 继续持有 String，旧 `drain`、`publish` 和 `append_with_imu` 接口保留。新增 `SharedImuSample` 使用只读 Arc<str>，SDK 回调共享初始化时验证的两份 frame ID，不逐条分配/复制字符串。共享与拥有样本的 JSON 字节一致，旧读取器仍返回拥有样本。
- SDK 和 Runtime 各复用一个数组；清空/预留在锁外，锁内检查错误和超时，再常量交换数组及取得一致的计数快照。正常排空从两次锁定变成一次，不在锁内分配收集数组。兼容拥有接口也复用自己的备用数组，但返回拥有字符串仍需分配。
- 原生录制池按整对队列容量 Q 固定 Q+3 个数组配额；首次有效样本才创建池，数组首次取用时在锁外预留 128 条容量，之后归还复用。成功、发送失败、关闭和放弃均回收批次；不耗尽后无限分配。每批和待提交样本仍限 128 条，整对队列容量不变。
- Runtime 到待提交批次通过移动合并，合并是锁外的线性操作。写索引借用 IMU 切片，删除原有 `imu.to_vec()`。仍有数字样本的正常搬移与 JSON 输出复制，不宣称整条路径零复制。
- 保留逐样本来源、数值和时钟检查；溢出/超时继续报错，未改成覆盖旧样本。录制格式、fsync、逐帧/索引哈希、提交守卫和恢复规则未改。

核查确认：chunked-v3 原有检查点累计读回加最终全量读回，IMU 验证次数应为提交数两倍；旧 files-v2 原本仅有提交前全量验证。本轮保持两种既有策略，没有将 files-v2 宣称为双轮格式。兼容性测试分别核对 V3 双轮计数和 V2 原计数。

## 测试与覆盖率

Linux 完整 Rust 工作区测试、外部测试、全部目标 Clippy 和格式检查通过。联合生产行覆盖率为 18353/18525 = 99.07%，没有修改过滤口径、排除规则或 99% 门禁。

新增测试覆盖：

- 共享 frame ID 的引用身份、拥有/共享 JSON 字节一致，以及共享样本仍拒绝错误 frame ID 和非有限数值。
- SDK 双数组地址交替、容量复用、原子排空计数与累计样本数一致、共享 frame ID 不随批次变化；预热后回调与复用排空不再产生 Rust 堆分配。
- 固定池配额耗尽、复用同一地址且不增加数组分配计数、队列满/关闭/放弃和写入后释放批次；待提交溢出仍失败，结束后排除样本仍计数，调用方数组保留容量。
- files-v2、chunked-v3 以共享切片和拥有样本写入时索引逐字节相同；反序列化后重编码也相同。原有两种 V3 检查点模式、两轮读回、损坏哈希拒绝、写入故障和崩溃恢复测试继续通过。

## 分配探针

分配数据取自带 LLVM 覆盖率插桩的独立 SDK ABI 子进程，不用于 CPU 计时。它在预热平台 mutex、SDK 线程和两条路径后，统计全部 Rust GlobalAlloc alloc/realloc（包含回调线程，不含 C SDK 的 malloc）。模拟加速度计、陀螺仪各 200 Hz。

- 共享路径：100 次复用排空、50 条样本，Rust 分配 **0 次**。
- 兼容拥有路径：16 条样本，Rust 分配 **25 次**。

后者是当前保留的拥有接口对照，不是旧二进制的完整分配剖析。SDK 使用两个重复数组地址；所有批次同类样本共享同一个 frame ID 存储。探针不覆盖 ROS C++ 消息构造、DDS、序列化输出扩容或离线 JSON 读取，不能外推为整个采集服务零分配。

## 交替性能对照方法

冻结旧提交并单独构建 release 服务；新旧服务在同一容器内交替运行，反转每轮先后顺序。两个场景各 5 次、两版本共 20 次。ARM64 主机上原生执行 aarch64 Linux Rust 1.90 release；模拟 SDK 与模拟 ROS C ABI 桥，640×400 YUYV/Y16、名义 30 FPS，IMU 双流各 200 Hz。仅发布场景就绪后测量 10 秒；原生录制使用同步 chunked-v3、300 对目标、1 GiB 上限。运行期间没有并行编译和其他测试。

CPU 为 worker/supervisor 的进程时间增量和除以测量墙钟时间，排除测试驱动与夹具编译；RSS 是两进程各自 VmHWM 之和，非同时峰值或匿名内存。追加和验证指标覆盖整个录制，包含就绪前已追加部分。P99 为固定直方图分位上界，不是原始精确分位。每次都要求图像无拒绝/缺对、录制完成、IMU 验证数恰好等于提交数两倍。

## 结果：5 次中位数

- 仅发布 before：吞吐 27.5991 对/秒；CPU 0.1050 核；RSS 合计 8896 KiB；IMU 排空 P99 上界中位数 61.439 μs。
- 仅发布 after：吞吐 27.5989 对/秒；CPU 0.1040 核；RSS 合计 9164 KiB；IMU 排空 P99 上界中位数 3.839 μs。
- 原生录制 before：吞吐 27.4808 对/秒；CPU 0.2106 核；RSS 合计 10928 KiB；IMU 排空 P99 上界中位数 180.223 μs。
- 原生录制 after：吞吐 27.5035 对/秒；CPU 0.2105 核；RSS 合计 11364 KiB；IMU 排空 P99 上界中位数 4.095 μs。

- 排空计时范围（每轮 P99 上界）：发布 before 45.055–147.455 μs；发布 after 3.583–6.655 μs；录制 before 163.839–212.991 μs；录制 after 3.071–5.119 μs。`drain_wall` 含锁等待、旧批次清空和数组处理，不是单独锁持有时间。持锁遍历改为常量交换，但未单独测量持锁 P99。
- 原生追加 P99 上界：18.874 → 18.874 ms；累计追加：655.642 → 664.097 ms。
- 累计验证：410.710 → 411.965 ms；单次验证 P99 上界：143.050 → 146.083 ms。
- SDK 队列峰值两版均为 14/128；新录制端每次实际预留数组均为 2 个，固定配额 7 个，没有随 300 对录制增长。
- RSS 中位数增加：仅发布 268 KiB、原生录制 436 KiB。没有测得内存节省；应接受这组结果中的常驻开销增加。RSS 包含进程全部代码和数据，不能将差值全归因于数组池。

CPU、吞吐、追加 P99 和验证耗时基本持平或存在波动。此次确认的收益是消除 SDK 回调/复用排空的稳态 Rust 分配、减少字符串与数组复制，以及明显降低观测到的排空尾延迟。发布桥、磁盘、哈希和读回仍占较多开销，不能把局部优化换算为整体 CPU 同比例下降。没有物理相机、USB 或实际 DDS 参与性能计时，实机收益仍待验证。

## 复现与原始数据

同名 JSON 保存 20 次完整观测、二进制 SHA-256、分配探针和覆盖率摘要。SDK 分配探针通过 `GDP_IMU_ALLOC_REPORT` 保存 JSON；子进程用于隔离计数，预热不算入测量。

```sh
GDP_IMU_BENCH_BASELINE_SERVICE=/absolute/before/capture-service \
GDP_IMU_BENCH_OUTPUT=/absolute/imu-buffers.json \
cargo +1.90.0 test --release --locked -p capture-probe --test service_supervision -- --exact imu_capture_ab_benchmark --ignored --nocapture

GDP_IMU_ALLOC_REPORT=/absolute/allocations.json \
cargo +1.90.0 test --locked -p orbbec-safe --test imu
```

Linux 容器测试使用 `--init` 保证孤儿进程回收。测试 SDK/ROS 桥均为合成夹具；没有改变真实设备配置或默认开启 IMU。
