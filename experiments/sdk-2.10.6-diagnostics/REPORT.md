## 功能、ABI 与数据保障

7 种 SDK 行为场景在原版、补丁关闭、补丁开启三组中，输出集合/帧数及包含类型、原序号、device/system 时间、载荷字节的行为摘要全部相同：完整配对、候选超窗、不完整集合输出、单流饥饿/聚合阈值、慢消费者输出队列溢出，以及 Pipeline 和聚合器两处真实 mutex 争用。精确计数与 ring 语义通过：候选超窗不是唯一丢帧数、聚合阈值命中不是实际排除、完整性策略排除与输出队列丢旧集合分别统计。

诊断单元测试验证：默认关闭无输出/无读时钟路径；非法、缺失、末级符号链接、组/其他可读目录拒绝；200 次排除及 200 次阈值事件后仅留最后 64 条、覆盖数 336；两个并发生产者的事件与 try-lock 放弃数精确合计；每进程 16 个活跃实例上限；锁 wait/hold 的独立计时。删除诊断目录后，SDK 合成 Pipeline 仍成功输出目标 60 对，错误不抛回采集路径。常规文件 I/O 在故障存储上仍可能阻塞 SDK 销毁的 join，建议用本地有容量预算的 tmpfs，不能声称故障下退出有硬截止时间。

原版与实验库的 406 个公开 C 导出符号完全一致，版本接口都返回 21006。33 份公开 C/C++ 头逐文件 SHA256 一致；公开头清单摘要 `b6753f9d936617db43f09e90bcef483ac3d8da74e97d4eb908217f09cbe684a8`。新诊断类型仅在内部头，不新增公开接口。库二进制摘要：

- 原版：`fb227fa251e347fae436e45dc46325100f0e1ac1b2ab4af688c13a95764c5f09`。
- 实验：`2cf440a207adc4c7821e4ae0efcff6678779c49041a24aae4e6476c64d74dc9a`。

GDP 全 Rust 工作区及 329 项 Python 测试通过（其中 1 项既有环境条件跳过）。原有 Global 映射、共享 ROS context、V3 两轮实际读回计数、逐帧/索引哈希、损坏拒绝、提交故障、SIGKILL/前缀恢复均继续回归。新增 SDK 采样器测试验证私有、有界、非符号链接文件及事件游标的初始/后续遗漏区分。该 GDP 回归沿用受控 SDK/mock 输入，不是把实验 SDK 接入物理相机后的联合验收；生产运行清单与固定 SDK 来源/摘要门禁未改。

## 开销方法

每组 5 轮，逐轮反转原版 before、补丁关闭 off、补丁开启 on 的顺序；每组同时运行 3 个独立进程，每个进程 1 个真正的 SDK Pipeline/FrameAggregator，内存设备和 2×2 图像。每种负载每个版本 15 个进程样本，这些属于 5 个并行组，不当作 15 次独立环境重复。没有并行编译或其他程序测试；主机与虚拟化调度、CPU 频率等背景波动仍存在。

无节奏吞吐每进程固定输入 100000 对；30 FPS 每进程 8 秒、240 对。CPU 为整个进程所有线程的 user+system 时间，包括对象初始化/销毁、FrameFactory 与报告线程；callback P99 是 onFrameCallback 驱动调用耗时的排序分位，排除驱动创建 Frame 的时间，**不是 SDK 全链路、ROS 发布或录制追加 P99**。CPU 高吞吐比较用固定工作量 CPU 秒，不用已接近饱和的核数判断成本。

第一组 [overhead-v1.json](reports/overhead-v1.json) 保留全部 90 个进程样本。后发现 getrusage.ru_maxrss 多数读数被 Python 启动进程的约 51 MiB exec 前高水位覆盖，不是真正 SDK 进程的 post-exec VmHWM，因此该组内存值标记为无效，不用于“内存不变”结论。原数据不删除。

随后只修正驱动在计时结束后的内存读取，SDK 诊断库未变，重测相同 5 轮三进程 30 FPS 场景，共 45 个进程样本，见 [paced-vmhwm.json](reports/paced-vmhwm.json)。当前驱动读取 /proc/self/status VmHWM，同时保留 ru_maxrss；修正组 VmHWM 为 12060–13364 KiB，而 ru_maxrss 仍为 52084–52340 KiB，确认两者范围不同。两个版本驱动二进制摘要独立保留；用 probe-metric-v1.patch 可从当前驱动重建旧口径。

## 结果

以下均为单进程样本中位数，不是三个进程的同时总峰值。

无节奏吞吐（原数据组）：

- before：CPU 41.3496 s，墙钟 43.4098 s，callback P99 7.584 μs。
- off：CPU 41.5181 s，墙钟 43.2601 s，callback P99 6.000 μs。
- on：CPU 43.1097 s，墙钟 44.9714 s，callback P99 7.292 μs。

CPU 中位数 off 相对 before +0.41%，on 相对 off +3.83%，on 相对 before +4.26%。callback P99 on 相对 off 增加 1.292 μs，但仍低于原版中位数，不能据此称诊断加速。CPU 秒范围 before 39.196–71.050、off 38.047–58.934、on 40.811–54.762，波动和重叠较大，百分比只是本批中位数，不能声称稳定的开销上限。

第一组 30 FPS 数据：

- before：CPU 0.033976 核，callback P99 111.876 μs。
- off：CPU 0.032640 核，callback P99 128.792 μs。
- on：CPU 0.033540 核，callback P99 138.875 μs。

修正内存口径后的 30 FPS 数据：

- before：CPU 0.038484 核，callback P99 149.584 μs，VmHWM 12568 KiB。
- off：CPU 0.039028 核，callback P99 143.459 μs，VmHWM 12744 KiB。
- on：CPU 0.038716 核，callback P99 148.000 μs，VmHWM 13100 KiB。

后一组 on 相对 off 的 CPU 中位数略低约 0.000312 核，不视为诊断节省 CPU。CPU 核数范围 before 0.03689–0.04332、off 0.03648–0.04374、on 0.03271–0.04444，明显重叠；两批 30 FPS 数据整体也发生漂移。callback P99 范围依次 84.084–235.167、79.708–205.251、98.208–260.584 μs，没有证据声称稳定改善或严格上限。

有效 VmHWM 中位数 on 比 off 增加 356 KiB，比原版增加 532 KiB；包含代码页、分配器、线程栈/TLS、状态和格式化工作区等，不能把差值全部归因于事件数组。关闭路径也增加 176 KiB 的中位数，范围相互重叠，不把该差值解释成固定常驻内存。它们不是匿名内存、容器工作集或实际三相机总内存。

## 采用结论与下一步

功能上可进入受控实机诊断：默认关闭、私有且有界的统计、后台文件输出以及失败隔离已验证。默认关闭没有测出明显稳定 CPU 回退；开启后最大吞吐场景的 CPU 中位数有约 4% 代价，30 FPS 下绝对 CPU/回调尾延迟较小但有噪声，不能声称全负载零开销。

继续保持默认关闭，现场先用相同构建配置的原版/补丁关闭/补丁开启交替运行，再通过真实 SDK 排除计数、队列峰值、两处锁 wait/hold、GDP SDK 等待/IMU 排空/ROS 发布、录制检查点阶段和磁盘压力定位。若是配对筛选主导，第二阶段再讨论配对策略；若是锁 hold/队列溢出主导，再讨论回调解耦。不能用本实验声称已修复约 66 ms 深度缺口、提高物理帧率、减少丢样或证明断电恢复。
